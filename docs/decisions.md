# Decision log

Newest last. Each entry: what, and why. Add a line when a design changes, in
the same commit as the change.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-09-30 | **Voice is the main demo**, built in M2, before the builder API | It's the riskiest part and the one that shows best; doing it early keeps the demo safe |
| D2 | 2026-09-30 | **One turn at a time per conversation**: a lease claimed at the start of a turn (conditional `UPDATE`), 409 otherwise | Two messages at once would run the model twice and could place two orders |
| D3 | 2026-10-01 | **The turn runs inside its listener** (the SSE response or the voice pipeline) | Simple. A tab closed mid-reply loses that turn; acceptable for the MVP |
| D4 | 2026-09-30 | **The transcript is stored per turn** (`turns.messages`), only ever added to | No growing blob to rewrite, and each turn shows exactly what the model saw |
| D5 | 2026-10-01 | **Jev (the Decider) does the commit check, and it fails closed.** Hand-off is a tool the model calls | Saving an order is the one step that can't be undone; an independent check guards it |
| D6 | 2026-10-01 | **Waiting lines are scripted, never in the transcript**: web shows a tool's `label`, voice says its `filler` | The line must be instant and safe; a model that sees "let me check" in its history starts answering it |
| D7 | 2026-09-30 | **Display and spoken forms for every value** (`runtime/speech.py`); the channel picks in code | Models convert numbers to words unreliably; a read-back on voice must be exact |
| D8 | 2026-09-30 | **The greeting is stored as the first assistant message** | Otherwise the model doesn't know the visitor saw it, and greets twice |
| D9 | 2026-09-30 | **The current time is in the state note** | "Are you open now?" stays right in a long conversation |
| D10 | 2026-09-30 | **mypy, CI and JSON logs from the start** | Cheap now; `Confirmed[T]` only protects anything if a type checker runs |
| D11 | 2026-09-30 | **Every tool has a timeout** | A slow source must never mean a hung conversation |
| D12 | 2026-10-01 | **`publish` saves a new version only if the built result (config, prompt, tool specs) changed** | No duplicate versions; a change to the platform rules reaches the dev agent on restart |
| D13 | 2026-10-01 | **MVP scope: edge cases not worth their code are left out** (design §12) | The time goes into the normal path and the voice demo |
| D14 | 2026-10-01 | **Gigalogy's Maira is the default talking model; Groq stays one setting away** (`LLM_PROVIDER`) | The owner's choice. Maira takes one text query: no streaming, no tool calls, no prompt cache. So from day 5, ordering needs `LLM_PROVIDER=groq` |
| D15 | 2026-10-01 | **Simpler storage, no caching.** One `config` per agent, no versions or publish (replaces D12). The transcript is the conversation's `messages` list (replaces D4); no turn lease (replaces D2); each turn's trace is a log line. The system prompt is built every turn with the date and time at the end | The owner's call for the MVP: fewer tables and concepts to learn. Costs: an edit reaches conversations already in progress, two messages sent at once would both run, and no prompt cache |
| D16 | 2026-10-01 | **Gigalogy calls tools too: as JSON in its reply** (changes D14). The query lists the tools and asks for `{"tool": …, "arguments": …}`; `GigalogyLLM` turns that into a `ToolCall`, so the runtime is the same for every provider | The owner wants ordering on Maira, the default. Costs: less reliable than native tool calls (bad JSON comes back as a validation hint), and each tool step is another whole, unstreamed request |
| D17 | 2026-10-01 | **Items live in their own `items` table, in one shape for every preset.** Up to `MAX_ITEMS_IN_PROMPT` (60) they're listed in the prompt; above that the prompt gives the categories and the model uses `search_items` | Tools work for any business; a business edits one item, not a config blob. A short list in the prompt lets the model recommend with no extra round trip; search is for catalogues too big to list |
| D18 | 2026-10-02 | **Voice: Pipecat over its own WebRTC (SmallWebRTC), Silero VAD, Gigalogy's Chorus for speech-to-text, Piper for text-to-speech for now** (Q3, Q4) | Pipecat runs in our process and talks to the browser directly: no LiveKit server or account to fail in a live demo, and only the owner's paid Gigalogy endpoints cost money. Chorus is upload-then-poll, not a stream, so each utterance is sent when the VAD hears 0.5s of silence. Measured 2 Oct on the echo call: Chorus 1.8–2.4s warm (6–8s when it's slow), Piper 0.2s, first sound 2.1s after the last word. Piper is free and local until the owner's TTS is added; a free local Whisper can replace Chorus behind the same class if it's too slow |
| D19 | 2026-10-02 | **No `voice/sentences.py` or `voice/pipeline.py`: the turn runs inside `voice/call.py`, and the reply's tokens go straight to Pipecat's TTS**, which already speaks sentence by sentence | Pipecat does the sentence cutting, so our own copy would be code to keep in step for nothing. One file holds the whole call |
| D20 | 2026-10-02 | **Spoken forms come from `speakable()` just before the TTS, not from the tool results** (changes how D7 is applied). The model sees "৳1,030" and "7:30 pm" on every channel; on voice, each sentence it says is put into words by Python ("one thousand and thirty taka", phone numbers digit by digit) | One place instead of a channel switch in every tool and the state note. Python still makes the words, so a read-back is exact as long as the model copies the digits, which it does more reliably than writing number words |
| D21 | 2026-10-02 | **A conversation takes at most `MAX_TURNS` (60) visitor messages**; the next gets a 409 `conversation_full`: "please start a new one" | Every turn sends the whole transcript (D15, no summaries), so an endless chat gets slower and dearer each turn and would one day pass the model's context. 60 is far past a real order or message |
| D22 | 2026-10-04 | **One agent per business.** `agents.workspace_id` is unique and the API is `/api/agent` (singular): no agent ids in URLs, no list, no `agent_id` filters. A second `POST` is a 409. The dev workspace has one agent too; changing `DEV_AGENT_PRESET` re-points it | A small business has one front desk. A list of agents was a concept the owner never needed, and every route had to carry an id for it. (From the production-grade `frontdesk-api`, D25) |
| D23 | 2026-10-04 | **Two roles: owner and admin.** `users.role`. An owner belongs to one business and sees only it. An admin belongs to none (a CHECK keeps role and workspace together), is made only by `heydesk create-admin`, and acts inside a business with an `X-Business` header on the ordinary routes, re-checked against the database on every request. Every admin write, and every admin read of one thing, goes to the insert-only `audit_events`. An admin can suspend a business (its chat answers 404 `unavailable`; the owner can still log in) and reset a forgotten password | A real product needs someone to support and switch off a business without its password, and owners deserve a record of when that happened. Reusing the ordinary routes means there's no second copy of them for admins. (From `frontdesk-api`, D25) |
| D24 | 2026-10-04 | **Orders and messages are one `records` table with one inbox.** A job is a task in the preset; its record has a `job`, a `kind` (`order` or `request`, from the task's finishing tool), and the kind's own columns. One API: `/api/inbox`, `/api/records`. The tools' ports (`Orders.place`, `Requests.submit`) don't change, so `runtime/` and `tools/` don't notice. Status changes follow a per-kind flow and an impossible one is a 409. Numbers are per business and kind, so a message now has one too | Two tables and two endpoint sets for the same idea; a new kind of job (bookings) would have meant a third. The owner sees one list. (From `frontdesk-api`, D26, without its booking kind) |
| D25 | 2026-10-04 | **Owners edit their business, not the engine.** The role text (`instructions`) and the `tools` come from the preset and only an admin may change them; an owner's PATCH with either is a 403. Owners get `notes`: free text for tone and rules, put in the prompt right after the role text | `instructions` is where a prompt can be broken (or told to ignore the platform rules), and `tools` decides what the agent may save; neither is something a small-business owner can judge. `notes` keeps the freedom they need. (From `frontdesk-api`, D27) |
| D26 | 2026-10-04 | **A business can start from just a preset, and is told what's missing.** The business name, agent name and timezone have defaults; the knowledge's address and hours start empty (left out of the prompt until set); `GET /api/agent` returns `missing`, a list in plain words (address, hours, items, a hand-off contact). Edits stay live (D15): no draft, preview or publish step | An owner's first screen shouldn't be a validation error. A checklist replaces frontdesk-api's draft/publish readiness (its D27) because HeyDesk has no versions to publish |
| D27 | 2026-10-04 | **Items carry their own facts: `attributes`, a JSON dict of plain values** (strings, numbers, booleans, lists of strings). They show on the item's prompt line (`{days: sat, sun}`). Still one shape for every preset (D17) | A clinic's speciality and days, a shop's brand and calories have nowhere else to live, and a column per field per business doesn't scale. A plain dict keeps the table, the tools and the prompt the same for everyone |
| D28 | 2026-10-04 | **`search_items` takes conditions, and Python decides the matches.** Arguments: `query` words, `category`, `tags`, `min_price`/`max_price` (whole currency units), and `filters` on attributes (`equals`, `at_most`, `at_least`, `includes`). The agent's items are loaded and filtered in code (not SQL), ranked by how many words matched; the best 10 come back with the total. `Catalog.search(str)` becomes `Catalog.all()` | "Healthy, under ৳300, no dairy" is a few conditions, not a keyword. The model says what the visitor means; code says what is true, so it can't invent an item. In Python it behaves the same on SQLite and Postgres and is easy to test; it's fine up to a few thousand items per business, and SQL or a vector index can replace it behind the same tool |
| D29 | 2026-10-04 | **Items come in from a CSV**, sent as JSON text to `POST /api/agent/items/import` (no multipart dependency, easy in Swagger). Known columns (code, name, description, price, category, tags, available) are the item's fields; **every other column becomes an attribute**, with numbers, yes/no and `;`-lists recognised. A `mapping` renames a business's headers. A price like "৳1,200.50" becomes minor units; a missing code is made from the name. It replaces the items, like `PUT`, and nothing is saved until every row is clean: problems come back per row, in one 422 | Most small businesses already have a spreadsheet, with their own column names; typing items into an API doesn't scale. All-or-nothing, because it replaces the whole catalogue. Excel users save as CSV; `.xlsx` and sync from a shop platform can come later behind the same parser |
| D30 | 2026-10-04 | **A clinic preset, with doctors as items and an appointment *request* (not a booking).** The speciality is the item's category, the fee its price, and days, hours, languages and years are attributes. The `appointment` task collects doctor, day and time, name and phone, and `submit_request` saves it after a yes; the clinic phones to confirm. The role text forbids diagnosing and sends emergencies to the emergency number and a hand-off | Proves the data layer on a second kind of business with no new table or tool. A real booking needs a free-slot source and a double-booking guarantee (frontdesk-api's `bookings`), which is a bigger step; a request the front desk confirms is how most small clinics already work |
| D31 | 2026-10-04 | **A time must be inside the opening hours, and Python works out the date.** `time_today` (pickup) and a new `appointment_time` check the business's `hours` (open inclusive, close not); a refusal says the hours, so the model asks for another time. `appointment_time` reads a day and a time ("tomorrow at 5 pm", a weekday, "5 Oct 6:30 pm"), within the next 14 days, saved as an ISO local time and shown as "Wed 30 Sep, 5:00 pm". No hours set yet means only the clock is checked. The clinic's `day_time` free text is replaced by it | A real clinic chat booked 11 pm for a clinic that closes at 10: the time was free text, and a restaurant's pickup time had the same gap. "Python does facts" (rule 1) means times too. Still unchecked: that the chosen doctor sees patients that day |
| D32 | 2026-10-04 | **What an agent can do is a list of jobs the owner switches on or off.** Order, appointment and message live in one shared library (`presets/jobs.yaml`), each with an owner-facing sentence; a preset only names the jobs on at first. `AgentConfig.jobs` replaces `tools` (a migration turns old tools into jobs), and the tools are worked out from the jobs, with hand-off always on. A job that is off isn't in the prompt's Tasks section, and the prompt says to offer a message or a person for anything else. The appointment job's first detail is now the generic `with` (who or what), so any business can use it. Supersedes D25's admin-only `tools` | Owners had no way to say what their agent does, and every preset repeated the same jobs. A clinic can now take orders and a restaurant appointment requests with no new code. Tools are an implementation detail the owner shouldn't see (D25's point), and deriving them means a job can't be on without the tool that saves it. (From `frontdesk-api`, D26) |
| D33 | 2026-10-04 | **Documents are searched by meaning and by exact words together (hybrid), embedded by Gemini, stored in Qdrant.** An `Embedder` port (`GeminiEmbedder`: `gemini-embedding-2`, 768 dimensions, over httpx; a deterministic `FakeEmbedder` for tests) and a pure chunker (about 1,200 characters, break at paragraphs then sentences then words, a 150-character overlap, a heading stays with its paragraph; the Bengali danda ends a sentence). Words are cut by Unicode category, not `\w`, so a Bengali word isn't split at its vowel signs. A failed embedding is one `EmbeddingUnavailable` that never repeats the response | A business's documents mix meaning questions ("when are you open late?") with exact strings (a price, a doctor's name, a phone number, Bengali and English in one line). Dense search alone misses the exact string; keywords alone miss the paraphrase; Qdrant fuses both in one query. Gemini is the owner's choice: no model to host, good Bengali, and a key already in `.env`; the port keeps a local model one adapter away. Document text goes to Google |
| D34 | 2026-10-04 | **Qdrant holds the chunks, behind a `KnowledgeStore` port; the SQL database stays the source of truth.** One collection for every business, told apart by a `workspace_id` payload (a tenant index) that every query filters on. Each chunk has a dense vector (cosine) and a sparse vector (hashed words, IDF applied by Qdrant, a saturating term weight); a query asks for both and Qdrant fuses them by reciprocal rank fusion. If the question can't be embedded, the search is words only. A dense floor (`dense_min_score`) keeps unrelated chunks out. No `QDRANT_URL` means Qdrant's local mode on disk, so development needs no cloud; tests use its in-memory mode, the real engine | One call, one fused ranking, filtered per business, with nothing to run ourselves (Qdrant Cloud's free tier). The full text of each document lives in SQL (next step), so the index can always be rebuilt |
| D35 | 2026-10-04 | **The agent searches documents with a tool, `search_knowledge`, only when the business has any.** The prompt lists the document titles and says to call it before saying "I don't know"; what comes back is labelled facts, never instructions; nothing found means "I'm not sure", plus an offer of a message or a person. The FAQ text stays in the prompt. The question is embedded, searched in Qdrant (hybrid, filtered to the business) and the best 4 passages return with their titles | A tool, not text pasted into every turn: a turn that doesn't need a document pays nothing, and the model decides when to look. The cost is one more model round trip when it does (about 2.5 s on Maira), so the tool has a voice filler and a web status line. Treating passages as data and sending an unanswered question to a message is the guard against a document that says "ignore your rules" and against the agent making things up |
| D36 | 2026-10-04 | **A section is a chunk, and a similarity floor of 0.6 keeps clearly unrelated text out.** A Markdown heading starts a new chunk (no overlap across it), so a section is searched on its own. Measured live on 4 Oct against Gemini (9 questions, English and Bengali, a 5-section guide): the right section ranked first every time, scoring 0.69 to 0.79 against 0.58 to 0.64 for the runner-up; questions the guide doesn't answer scored 0.50 to 0.60. So `KNOWLEDGE_MIN_SIMILARITY=0.6` drops the dense match for text that isn't similar at all; exact-word matches ignore it. It is a floor, not a judge: scores overlap near the edge, so the agent still decides from the passages (D35) | Packing small sections into one chunk made "how much does Dr. Hasan charge" land on a chunk of hours and fees. A cut-off set from data beats a guess, and a low floor costs only a little noise, where a high one silently turns answerable questions into "I'm not sure". The sample is small (9 questions): re-measure with a real business's documents |
